<objective>
## Goal
Implement the `manifest` family (V-MAN-001..006) over BTDS Annex B manifests and `cards.json`, with a dependency-free JSON Schema validator covering exactly the keywords the Annex B schemas use — and skipping, not passing, when a schema uses anything else.

## Purpose
Manifests are the single source of truth for card values and expected Application Catalog contents. Today their schema is hand-checked; known divergence (cards `proposed` while their folders are built) is exactly what V-MAN-004 should surface.

## Output
- `lib/jsonschema.js` subset validator
- `lib/families/manifest.js` replacing the stub
- Synthetic fixtures + tests; README status
</objective>

## Facts (private AtlantisPB checkout; conventions only)
- layout.json preset key `annexB` → `docs/annex-b`. Under it: `manifest-schema/{manifest,cards}.schema.json`, `manifests/cards.json`, `manifests/g00N/st3-f-pcap-NNN.json`. Sub-paths are documented in `manifest-schema/README.md`, not in layout.json.
- Keywords used by both schemas: `$schema $id $defs $ref title description type properties required additionalProperties items enum const pattern minLength minItems minimum uniqueItems allOf if then`.
- cards.json: `{ cardsVersion, status, virtualChannelPlan, cards: [{ label, virtualChannel "10.1", applicationId, state: built|proposed|…, builtIn?: "applications-staging/<slug>", … }] }`.
- Manifest: `{ manifestVersion, id: "ST3_F_PCAP_001", group, cases: [ST3_F_TC_…], signaling: { applications: [{ card }] }, expectedCatalog: { orderRule, entries: [{ card, virtualChannel, … }] }, combinations: [{ expectedCatalog }] , … }`. `card` keys appear at any depth.
- catalog.findCase(id) → `{ artifacts: [{ id, type, primary }] , … }`; catalog.findArtifact(pcapId).cases.
- `applications-staging/` holds filler folders (layout `fillerGroup`).
</context>

<acceptance_criteria>

## AC-1: Schema subset validator
```gherkin
Given a schema using only supported keywords (list above, $ref to local "#/$defs/…")
When validating an instance
Then it returns errors with JSON Pointer instance path and the failing keyword
And annotation keywords ($schema, $id, title, description, $comment, examples, default) are ignored
And a schema containing any other keyword (anywhere) is reported as unsupported with the keyword list — validate() is not attempted
```

## AC-2: V-MAN-001 schema validation
```gherkin
Given <annexB>/manifest-schema/ and <annexB>/manifests/
Then every st3-f-pcap-*.json validates against manifest.schema.json and cards.json against cards.schema.json
And each validation error → blocking finding (path, pointer, keyword)
And invalid JSON → blocking finding with the parse message
And missing schema file or unsupported keyword → skipped with reason (per schema, all files using it)
And annexB path from layout.json; missing → skipped "annexB not in layout"
```

## AC-3: V-MAN-002 manifest cases ↔ catalogue
```gherkin
Given a manifest with id P and cases[]
Then P equals the ID from the file name and exists in the catalogue
And every case exists (catalog.findCase) and cites P among its artifacts
And catalogue cases citing P that the manifest omits are reported too (both directions)
And adapter unavailable → skipped
```

## AC-4: V-MAN-003 card references
```gherkin
Given every `card` string at any depth of a manifest
Then it must be a label in cards.json; unknown → blocking finding with JSON pointer
And cards.json missing/invalid → skipped
```

## AC-5: V-MAN-004 built cards ↔ staging folders
```gherkin
Given cards.json
Then a card with state "built" must have builtIn pointing to an existing folder
And a card with builtIn whose folder exists but state ≠ "built" → should-fix (the known A03/B01/B02 divergence)
And every folder in the filler group dir (layout fillerGroup, fallback applications-staging) must be some card's builtIn
```

## AC-6: V-MAN-005 ordering, V-MAN-006 unique channels
```gherkin
Given every expectedCatalog object (any depth) whose orderRule mentions ascending virtual channel
Then its entries that carry virtualChannel are in ascending numeric (major.minor) order; violation → should-fix naming the first out-of-order pair
And V-MAN-006: duplicate virtualChannel values across cards.json → blocking, listing the labels
```

## AC-7: Targets and real run
```gherkin
Given targets (PCAP IDs or paths)
Then only matching manifests are checked; cards-level checks (004, 006) run when no target or a target is cards.json/annexB dir
And a real AtlantisPB run is explainable (A03/B01/B02 expected under V-MAN-004), recorded in SUMMARY, not committed
```
